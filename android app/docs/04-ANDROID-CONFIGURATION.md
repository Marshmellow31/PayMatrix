# Android Configuration

## Document status

This document defines the Android environment, project, manifest, App Links, signing, secret handling, testing, and release configuration for PayMatrix. It is documentation only. No application code, package file, manifest, Firebase setting, or Play Console setting has been changed by this document.

Target package: `com.paymatrix.app`

Target Firebase project: `paymatrix-174b5`

Production host: `pay-matrix.vercel.app`

## Separation from the web app

The existing web application remains in `frontend/`. Android-specific dependencies, Capacitor configuration, generated Gradle project, signing configuration, and Android documentation belong under `android app/`.

Intended layout:

```text
PayMatrix/
  frontend/                         Existing web and PWA application
  android app/
    docs/                           Android implementation documents
    package.json                    Future Android wrapper dependencies
    package-lock.json               Future reproducible dependency lock
    capacitor.config.ts             Future Android wrapper configuration
    src/                             Future mobile-specific adapters and UI
    www/                             Generated mobile web bundle, not hand-edited
    android/                         Future generated native Android project
      app/
        google-services.json        Firebase Android configuration
```

Do not move the existing `frontend` package into this directory. Do not make the web deployment depend on Android Studio, Gradle, or `google-services.json`. The future mobile build may share application modules deliberately, but its package and build commands must remain independently runnable.

## Capacitor configuration baseline

The future `android app/capacitor.config.ts` should start with:

```ts
/// <reference types="@capacitor-firebase/authentication" />

import type { CapacitorConfig } from '@capacitor/cli';

const config: CapacitorConfig = {
  appId: 'com.paymatrix.app',
  appName: 'PayMatrix',
  webDir: 'www',
  server: {
    androidScheme: 'https',
  },
  plugins: {
    FirebaseAuthentication: {
      skipNativeAuth: true,
      providers: ['google.com'],
    },
  },
};

export default config;
```

Production rules:

- Do not configure `server.url` in a release build. Production assets must be bundled in the app.
- Do not configure broad `allowNavigation` entries.
- Keep `androidScheme: 'https'` so the Capacitor origin uses a secure context.
- Keep the package ID immutable after Play Console registration.
- Treat `www/` as generated output.

## google-services.json

Register `com.paymatrix.app` in the existing Firebase project `paymatrix-174b5`, add SHA fingerprints, and download the resulting file as described in `03-NATIVE-AUTH-AND-FIREBASE.md`.

Required path:

```text
android app/android/app/google-services.json
```

The file is Firebase client configuration, not a service-account private key. It contains identifiers and API keys that can be recovered from an APK. It must never be treated as an authorization control.

Recommended repository policy:

- A private repository may commit the production client configuration if that simplifies reproducible builds.
- A public repository may either commit it, because it is client-visible by design, or inject it during CI to reduce accidental project scraping. Security cannot depend on hiding it.
- Never place service-account JSON, private keys, OAuth client secrets, or Admin SDK credentials beside it.
- Redact the file from bug reports and chat logs unless its exact content is required for diagnosis.

## AndroidManifest baseline

The future `android app/android/app/src/main/AndroidManifest.xml` needs a standard Capacitor activity and the verified PayMatrix App Link.

Use this as a review target, not as a blind replacement for the generated manifest:

```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android">
    <uses-permission android:name="android.permission.INTERNET" />

    <application
        android:allowBackup="false"
        android:label="@string/app_name"
        android:supportsRtl="true"
        android:theme="@style/AppTheme"
        android:usesCleartextTraffic="false">

        <activity
            android:name=".MainActivity"
            android:configChanges="orientation|keyboardHidden|keyboard|screenSize|smallestScreenSize|screenLayout|uiMode|navigation|density"
            android:exported="true"
            android:launchMode="singleTask"
            android:theme="@style/AppTheme.NoActionBarLaunch">

            <intent-filter>
                <action android:name="android.intent.action.MAIN" />
                <category android:name="android.intent.category.LAUNCHER" />
            </intent-filter>

            <intent-filter android:autoVerify="true">
                <action android:name="android.intent.action.VIEW" />
                <category android:name="android.intent.category.DEFAULT" />
                <category android:name="android.intent.category.BROWSABLE" />
                <data
                    android:scheme="http"
                    android:host="pay-matrix.vercel.app"
                    android:pathPrefix="/join/" />

                    android:scheme="https"
```

## Permissions policy

### Required now

- `android.permission.INTERNET`: required for Firebase, Functions, remote images, and API calls. It is a normal install-time permission.

### Not required for Google account selection

- `GET_ACCOUNTS`.
- Contacts permissions.
- Phone permissions.
- SMS permissions.
- Biometric permissions.
- Location permissions.

Credential Manager and Google Play services present the chooser. PayMatrix does not need direct access to the device account list.

### Add only when the matching native feature is implemented

- `POST_NOTIFICATIONS`: needed at runtime on Android 13+ for native push notifications.
- Camera permission: only if PayMatrix adds direct native camera capture rather than a system picker or browser capture flow.
- Media permissions: only if a feature directly reads user media. Prefer Android Photo Picker and Storage Access Framework.

Never request `MANAGE_EXTERNAL_STORAGE`. Avoid legacy broad storage permissions. Use scoped storage, the system document picker, share sheet, and MediaStore as appropriate.

Before release, inspect the merged manifest rather than only the source manifest:

```powershell
Set-Location "C:\Users\1080p\Desktop\personal projects\PayMatrix\android app\android"
.\gradlew.bat :app:processReleaseMainManifest
```

Review the merged manifest in Android Studio and remove any unnecessary permission introduced by a dependency.

## Network security and local development

Release builds must use HTTPS and set `android:usesCleartextTraffic="false"`. Firebase production endpoints and `https://pay-matrix.vercel.app` are HTTPS.

If local Android development must connect to an HTTP emulator endpoint, allow cleartext only in the debug source set with a debug-only network security configuration. Do not weaken the main or release manifest. Android emulator host loopback is `10.0.2.2`, not `localhost`.

Examples for a debug environment:

```text
Functions emulator from Android emulator: http://10.0.2.2:5001
Vite dev server from Android emulator:      http://10.0.2.2:<port>
```

The current web Firebase configuration automatically connects Functions to `localhost:5001` whenever `import.meta.env.DEV` is true. The mobile implementation must make the host configurable because `localhost` inside the emulator is the emulator itself.

Never ship a production build that points to a Vite server, Firebase emulator, local IP address, or `server.url`.

## Backup and local data

PayMatrix stores a cached profile in `localStorage` and Firebase SDKs maintain authentication state. For a financial utility, the simplest production baseline is `android:allowBackup="false"`.

If product requirements later require Android backup, create explicit Android 12+ data extraction rules and legacy full-backup rules that exclude WebView data, Firebase auth persistence, local databases, cached exports, and any file containing user data. Do not enable broad backup without a restore test across devices and accounts.

On logout, clear Redux data, `paymatrix_user`, in-memory service caches, Firebase JavaScript auth state, and Credential Manager state. Verify that signing in as another account cannot display the previous user's cached groups or profile.

## Android App Links

### Supported link

The current web route is:

```text
https://pay-matrix.vercel.app/join/{code}
```

The Android App Link should initially claim only `/join/` paths. Broaden the manifest only after the app implements and tests additional routes.

### Publish assetlinks.json

The future web deployment must serve this file at:

```text
https://pay-matrix.vercel.app/.well-known/assetlinks.json
```

For the Vite app, the source file should eventually be:

```text
frontend/public/.well-known/assetlinks.json
```

Template:

```json
[
  {
    "relation": ["delegate_permission/common.handle_all_urls"],
    "target": {
      "namespace": "android_app",
      "package_name": "com.paymatrix.app",
      "sha256_cert_fingerprints": [
        "DEBUG_OR_LOCAL_RELEASE_SHA256",
        "PLAY_APP_SIGNING_SHA256"
      ]
    }
  }
]
```

Use actual SHA-256 certificate fingerprints. Include the certificates needed by the environments being tested. The Play App Signing SHA-256 is mandatory for links opened by Play-distributed builds.

Hosting requirements:

- HTTPS only.
- HTTP status 200.
- No login, cookie, or authentication requirement.
- No redirect from the exact `/.well-known/assetlinks.json` path.
- Valid JSON with no comments.
- `application/json` content type is preferred.
- The file must remain publicly readable.

### Route incoming links

The future React mobile entry point must use `@capacitor/app` and handle both warm and cold starts:

```js
import { App as CapacitorApp } from '@capacitor/app';

const allowedOrigin = 'https://pay-matrix.vercel.app';

function routeAppUrl(rawUrl, navigate) {
  const url = new URL(rawUrl);
  if (url.origin !== allowedOrigin) return;
  if (!url.pathname.startsWith('/join/')) return;
  navigate(`${url.pathname}${url.search}${url.hash}`);
}

export async function installAppLinkRouting(navigate) {
  const launch = await CapacitorApp.getLaunchUrl();
  if (launch?.url) routeAppUrl(launch.url, navigate);

  return CapacitorApp.addListener('appUrlOpen', ({ url }) => {
    routeAppUrl(url, navigate);
  });
}
```

Validate the origin and allowed path before routing. Do not navigate arbitrary incoming URLs into the WebView.

The existing `JoinGroup` route stores `pendingInviteCode` and redirects an unauthenticated user to login. Preserve this behavior so the native account chooser can complete and then resume the invite.

## Android back behavior and gestures

The system back button and Android predictive back gesture must follow navigation history before exiting the app.

Implementation requirements for the later code phase:

- Use `@capacitor/app` `backButton` handling only when custom behavior is required.
- If an in-app modal, drawer, sheet, or full-screen dialog is open, close it first.
- Otherwise, if React Router can go back within PayMatrix, navigate back once.
- At the root dashboard, allow the default Android behavior or require a deliberate second back action before exit.
- Never trap the user in the app by swallowing every back event.
- Do not add a visible custom back button where Android system navigation already provides the expected action, except in nested app screens where an app-bar back control is standard.
- Test both three-button navigation and gesture navigation.

Android 13+ predictive back support should be tested on a physical device and emulator. Keep Capacitor and AndroidX Activity current within the supported major so native back dispatch integration remains compatible.

## Refresh rate and rendering configuration

Android WebView normally renders at the display's active refresh rate when frames are produced quickly enough. Do not force a fixed 60 Hz frame rate.

Production requirements:

- Use the current Android System WebView or Chrome provider.
- Test on 60 Hz, 90 Hz, and 120 Hz devices.
- Avoid JavaScript work longer than one frame: about 16.7 ms at 60 Hz, 11.1 ms at 90 Hz, and 8.3 ms at 120 Hz.
- Animate only `transform` and `opacity` where practical.
- Avoid large blur regions, continuous backdrop filters, and layout-triggering animations on core screens.
- Virtualize long activity and member lists.
- Move receipt parsing and expensive calculations off interaction-critical paths.
- Pause animations when the app is backgrounded.
- Use Chrome DevTools remote inspection and Android Studio CPU/System Trace to measure, not guess.
- Run release builds for performance tests because debug builds and remote debugging add overhead.

No manifest flag can guarantee lag-free 120 Hz rendering. It requires measured frame pacing, bounded JavaScript work, efficient React rendering, and appropriately sized assets.

## Signing and secret handling

### Create one upload key

Create the upload key outside the repository:

```powershell
New-Item -ItemType Directory -Path "D:\secure" -Force
& "$env:JAVA_HOME\bin\keytool.exe" -genkeypair -v `
  -keystore "D:\secure\paymatrix-upload.jks" `
  -alias paymatrix-upload `
  -keyalg RSA `
  -keysize 2048 `
  -validity 10000
```

Back up the keystore and passwords in a secure password manager or encrypted backup. Losing the upload key creates an account recovery process and can block emergency releases.

### Never commit

- `*.jks`, `*.keystore`, or signing certificates with private keys.
- Keystore passwords or aliases paired with passwords.
- `keystore.properties` containing credentials.
- Service-account JSON.
- Firebase Admin SDK private keys.
- Google OAuth client secrets.
- Gemini or other server API secrets.
- Play service-account keys.

The future Android repository rules should ignore at least:

```gitignore
*.jks
*.keystore
keystore.properties
local.properties
```

Load release signing values from environment variables or an ignored local property file. In CI, store the keystore as an encrypted secret and reconstruct it only for the build job. Ensure CI logs never print passwords or base64 keystore contents.

### Play App Signing

Enable Play App Signing. Upload an Android App Bundle signed with the upload key. After Play creates the app-signing certificate:

1. Add its SHA-1 and SHA-256 to Firebase Android app settings.
2. Add its SHA-256 to `assetlinks.json`.
3. Download a fresh `google-services.json` if Firebase OAuth configuration changed.
4. Upload a new internal-test bundle.
5. Verify Google login and App Links from the Play-installed build.

## Native push notification warning

The current web app initializes Firebase Web Messaging and stores a web FCM token. A WebView is not a production substitute for native Android push registration.

Before Play release, implement and test native FCM using a Capacitor-compatible Firebase Messaging plugin. Required follow-up work includes:

- Request `POST_NOTIFICATIONS` on Android 13+ after an in-context prompt.
- Obtain a native Android FCM registration token.
- Store tokens per user and per installation, rather than one undifferentiated `fcmToken` if web and Android can both be active.
- Remove stale tokens on logout and invalid-registration responses.
- Handle foreground, background, and notification-tap routing.
- Route notification data URLs through the same allowlisted navigation function used for App Links.
- Guard or disable Firebase Web Messaging initialization inside the native WebView.

The existing Cloud Function already includes top-level notification and data payloads in addition to `webpush`, so its payload is close to cross-platform. The token storage model and native client registration still require implementation and regression testing. Review backend changes when native messaging is added.

## End-to-end test matrix

### Devices

- Minimum supported Android 7 / API 24 device or emulator.
- Android 10 or 11 mid-range device.
- Android 13 device for notification permission behavior.
- Android 15 and Android 16 devices for current platform behavior.
- 60 Hz and high-refresh-rate devices.
- Gesture navigation and three-button navigation.
- Small phone, large phone, and tablet or foldable layout check.

### Lifecycle and navigation

- Cold launch, warm launch, background resume, and process recreation.
- Back button closes overlays, goes through history, then exits at root.
- Predictive back gesture does not freeze or expose blank content.
- App Link opens when app is closed, backgrounded, and foregrounded.
- Invite link survives native sign-in.
- Rotation, font scaling, display scaling, dark mode, and keyboard opening do not reload or corrupt state.

### Performance

- Dashboard first meaningful content on a mid-range device.
- Scroll activity and group lists without repeated long frames.
- Open and close every modal and drawer without layout jumps.
- Add expense, calculate balances, scan receipt, and export flows under release build.
- Inspect Android vitals or local frame timing for jank and ANRs.
- Test slow network, offline launch, reconnect, and Firebase listener recovery.

### Security

- No tokens or secrets in Logcat.
- No previous-user data after logout and account switch.
- Firestore rules reject unauthenticated and unauthorized requests.
- Admin UI and Functions require the `admin` custom claim.
- App Link router rejects wrong hosts and unsupported paths.
- Release build rejects cleartext network traffic.
- Backup or data extraction behavior matches the declared policy.
